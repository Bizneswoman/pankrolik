# RCA — Admin login "Nieprawidłowe hasło" on production (Pan Królik / elegant-rabbit)

## Problem statement
Production `/admin` login at `https://elegant-rabbit.emergent.host` reportedly always returns "Nieprawidłowe hasło" (wrong password) even with the correct password `pankrolik2025`. Two hypotheses to test: (a) wrong/overridden `ADMIN_PASSWORD` in prod, or (b) a DB connection failure returning HTTP 500 that the admin UI renders as "wrong password".

## What I checked and found (production, active run a40d32c7)

### 1) POST login status (200 / 401 / 500)
- Could NOT directly execute the POST: the ephemeral sandbox failed to spawn repeatedly (platform-side, `eph_spawn_failed` / "pod reached terminal phase Failed"), and no tool performs an arbitrary HTTP POST. So the exact POST result is **UNVERIFIED**.
- Indirect probe: `GET https://elegant-rabbit.emergent.host/api/admin/login` → **HTTP 404** in ~1424 ms, body `{"error":"Route /admin/login not found"}` (clean JSON from the app's own router; GET isn't a valid method for this route). Per the described architecture, `connectToMongo()` + `ensureSeed(db)` run on EVERY API call before routing — so a reachable-404 (not 500) means **connectToMongo succeeded**. If Mongo were unreachable this GET would have 500'd. The ~1.4s latency is consistent with a real DB connect occurring.

### 2) Production env vars
- `list_secrets` (active run): **`ADMIN_PASSWORD` is NOT present at all** in production. => code falls back to the default `'pankrolik2025'`. So there is **no wrong/overridden password** in prod. (Hypothesis (a) DISPROVEN.)
- `MONGO_URL`: present (non-empty). `DB_NAME`: present (non-empty).
- `mongo_query list_collections` resolved the production `MONGO_URL` server-side → `db_name = "elegant-rabbit-your_database_name"`, collections `[content, gallery, menu, reviews]`. This is the **platform-managed MongoDB**, **NOT the user's Atlas cluster** (`pankrolik.dgdgjsi.mongodb.net`, DBs `pankrolik`/`test`). The query succeeded, so prod Mongo is **reachable and seeded**.
- Note: `MONGO_URL` is a platform SYSTEM key — it is regenerated to the managed Mongo on every deploy and overwrites any user/preview value. Production therefore does not and cannot use the user's own Atlas via the Secrets tab. The user's recent Atlas IP-allowlist / DB-user password-reset work has **no bearing on production**.

### 3) Runtime logs
- `fetch_app_logs` (run a40d32c7, last 1440 min): 16 lines total, all clean startup for two replicas (`✓ Ready in 838ms`, `Starting Next.js app: node server.js`). **No MongoDB errors, no "bad auth", no server-selection timeout, no 500s.** Pods are healthy.

## Root cause
Both reported hypotheses are disproven by the evidence:
- NOT a wrong/overridden `ADMIN_PASSWORD` — it is unset in prod, so the correct default `pankrolik2025` is in effect.
- NOT a DB-connection failure — the production managed Mongo is reachable (GET returns a routed 404 not a 500, `mongo_query` connected and listed seeded collections, and logs show no Mongo errors).

With the DB reachable and the default password active, `POST /api/admin/login {"password":"pankrolik2025"}` should return `{success:true}`. The most likely explanations for the user's observation are: (1) the report was captured during the earlier transient Atlas "bad auth" window — which only affected preview, since prod never uses Atlas; or (2) a client-side issue (stale cached admin bundle, or the admin UI treating any non-200 — e.g. a transient/404/network — as "wrong password"). The exact live POST could not be executed here because the sandbox was unavailable.

## Suggested next steps
1. Re-test login on the live prod URL in a fresh incognito window (clears any stale bundle). It is expected to succeed with `pankrolik2025`.
2. If it still fails, open DevTools → Network, submit the login, and capture the `POST /api/admin/login` **status code + response body**. That single data point disambiguates: 500 = DB/server error, 401 = password mismatch, 404/CORS/network = frontend wiring. Send it back to retrigger.
3. Decision item: if the user expects their own Atlas data/writes to be served in production, that will not happen — prod uses the platform-managed Mongo and `MONGO_URL` cannot be overridden to Atlas (SYSTEM key). Raising/using an external Atlas in prod needs a support conversation.

## Confidence
High that neither hypothesized cause is real (password unset; DB reachable, all tool-verified). The live POST result itself is UNVERIFIED due to sandbox unavailability.
